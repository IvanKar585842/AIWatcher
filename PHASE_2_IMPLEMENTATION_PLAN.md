# Phase 2 — план авторизации workspace

Анализ сделан по коду, не только по аудиту. Реализация идёт после этого файла, в той же фазе. Phase 3 не начинается.

## Текущая архитектура

Пользователя определяет Clerk: `auth()` даёт `clerkId`, `getOrCreateUser` находит строку `User`. Локальная сессия без Clerk есть только в development.

Монитор принадлежит `userId`. Мутации идут через `assertMonitorOwnedBy`. Чтение списка дополнительно пускает участников `Team`, если монитор расшарен. Это не изоляция агентства.

`Team` — одна команда на владельца, роли OWNER/MEMBER, инвайт-код без письма. Семантика другая: общий доступ к мониторам владельца. Workspace её не заменяет и с ней не сливается.

`Workspace.ownerId` уже есть. `Client` принадлежит одному workspace. У монитора `workspaceId` и `clientId` пустые. Триггер не даёт связать монитор с клиентом другого workspace. Ни один HTTP-маршрут эти поля пока не пишет: схема обновления монитора их не содержит.

## Модель участия

Новая таблица `WorkspaceMember`: пара `workspaceId` + `userId` уникальна, роль `OWNER | ADMIN | MEMBER | VIEWER`.

Владелец остаётся в `Workspace.ownerId`. При создании workspace в той же транзакции пишется membership с ролью OWNER. Сменить `ownerId` обычным запросом нельзя: поле не принимается API, триггер отклоняет UPDATE.

Один пользователь может состоять в нескольких workspace. Дубликат пары запрещён уникальным индексом.

Старый `Team` не мигрируется и не читается этими проверками.

## Роли

- OWNER: имя, удаление workspace, участники, инвайты, чтение клиентов и мониторов внутри workspace.
- ADMIN: имя, инвайты и снятие только MEMBER и VIEWER. Не удаляет workspace, не назначает OWNER и ADMIN, не трогает строку владельца.
- MEMBER: чтение workspace и участников. Запись клиентов и мониторов внутри workspace подготовлена правом, отдельных экранов клиентов в этой фазе нет.
- VIEWER: только чтение.

Проверка на сервере. Скрытие кнопок ничего не разрешает.

## Авторизация

Один слой: `src/lib/tenancy.ts` хранит чистые правила, `src/lib/workspace-access.ts` ходит в базу.

Правила:

- Нет членства и пользователь не владелец: ответ 404 `Not found` и для чужого id, и для отсутствующего. Так нельзя отличить «нет объекта» от «нет прав».
- `workspaceId` из запроса не доказательство. Сначала строка membership или `ownerId`, затем запрос данных только с этим id.
- Чтение и изменение членства идут в транзакции. Строка workspace блокируется `FOR UPDATE`, чтобы отзыв доступа не прошёл мимо уже начатой операции.
- Владелец не снимается и не понижается.
- Роль OWNER нельзя выдать инвайтом или сменой роли.

## Приглашения

Полноценная почтовая приглашалка через Clerk и Resend в этой фазе не делается: это отдельный поток подтверждения почты, и письма в разработке не отправляются.

Вместо этого одноразовый код, как у Team: хеш в базе, открытый код один раз в ответе создателю. Человек с уже существующим аккаунтом вводит код сам. Новых пользователей код не создаёт.

Инвайт не может иметь роль OWNER. ADMIN может выпускать только MEMBER и VIEWER.

## API

Новые маршруты только для workspace. Старые `/api/monitors`, `/api/teams`, Stripe, Clerk и cron не меняют правила доступа.

- `GET/POST /api/workspaces`
- `GET/PATCH/DELETE /api/workspaces/:id`
- `GET /api/workspaces/:id/members`
- `PATCH/DELETE /api/workspaces/:id/members/:userId`
- `POST /api/workspaces/:id/invites`
- `POST /api/workspaces/join`

PATCH workspace принимает только `name`.

## База

Миграция `20261113180000_workspace_membership`. Vercel по-прежнему собирает `npm run build` и миграцию не применяет. На прод этот SQL не запускается.

Удаление workspace по-прежнему отвязывает мониторы и удаляет клиентов. Участники и инвайты удаляются вместе с workspace. Мониторы и их история остаются.

## Риски

Прямой SQL может вставить согласованную пару client/workspace. HTTP этого пути не имеет.

Старые мониторы без workspace продолжают жить на `userId`. Membership их не открывает.

Гонка «проверили членство, потом его удалили» закрывается блокировкой строки workspace в той же транзакции, что и изменение.

## Тесты

`scripts/test-workspace-auth.ts` на локальной базе вызывает реальные функции доступа, не подмену. Покрывает роли, чужие id, самоназначение OWNER, отзыв, повторный инвайт и сохранность старого монитора.

Живые сетевые тесты fetch не запускаются: пайплайн загрузки не меняется.
