# Phase 2 — модель угроз авторизации workspace

Каждый сценарий закрыт серверной проверкой. Ответ отказа — 404, без различия «нет прав» и «нет объекта». Доказательство — `scripts/test-workspace-auth.ts` на локальной базе, если не сказано иное.

| Сценарий | Защита | Доказательство |
| --- | --- | --- |
| Чужой Workspace | `listWorkspaces` фильтрует по пользователю. Чтение по id требует membership или ownerId | stranger не видит id в списке и получает 404 на чтение |
| Подмена workspaceId | id из URL проходит `requireWorkspacePermission` до чтения данных | неизвестный и чужой id → 404 |
| Viewer меняет монитор | `monitors.write` нет у VIEWER. Старый PATCH монитора всё ещё требует `userId` владельца записи | viewer не переименовывает workspace. Отдельного workspace-PATCH монитора нет |
| Member удаляет Workspace | `workspace.delete` только у OWNER | member получает 404 |
| Admin передаёт ownership | PATCH принимает только `name`. `setMemberRole` отвергает роль OWNER. Триггер запрещает смену `ownerId` и второго OWNER | оба пути проверены |
| Участника сняли, сессия Clerk ещё жива | каждый запрос заново читает membership. Сессия Clerk не хранит роль | после `removeMember` чтение workspace и клиента даёт 404 |
| Сам добавился в чужой Workspace | membership создаётся только создателем workspace или погашенным кодом. Код выпускает тот, у кого есть `members.invite` | чужой список пуст до кода; повтор кода не пускает третьего |
| Сам назначил себе OWNER | `canGrantWorkspaceRole` и триггер `workspace_member_guard` | API 404 и исключение базы |
| Client другого Workspace | `assertClientVisible` берёт `workspaceId` из строки клиента и проверяет право на этот workspace | снятый пользователь получает 404 |
| Monitor другого Workspace | `assertMonitorVisibleInWorkspace` делает то же. Монитор без workspaceId этим путём не открывается | outsider и снятый участник получают 404 |
| Два изменения membership сразу | транзакция берёт `FOR UPDATE` по строке workspace | снятие участника ждало 700 мс, пока другая транзакция держала блокировку, и только потом завершилось |
| Право проверили, членство сняли до записи | блокировка workspace держится до конца транзакции. Чужое снятие ждёт эту транзакцию или видит уже удалённую строку | тот же тест ожидания блокировки |

Не проверялось отдельным тестом: два клиента Prisma одновременно меняют одну и ту же роль в обе стороны. Блокировка строки это сериализует, но исход «какая роль останется» зависит от того, кто захватил блокировку первым. Это не даёт права тому, у кого права нет.
