# Phase 1 Quality Audit

Дата: 13 ноября 2026.  
Объект: фундамент `Workspace` → `Client` → `Monitor`.  
Прод, секреты, Clerk, Stripe, домен и `AI_PROVIDER` не менялись. Production migration не запускалась.

## 1. Executive Summary

Phase 1 — это схема и ограничения базы, а не продукт агентства. Старые мониторы остаются на `userId` с пустыми `workspaceId` и `clientId`. Чужой клиент не привязывается к монитору. Удаление workspace или client не удаляет монитор, снимки и историю изменений.

В аудите найден пробел: состояние «клиент указан, workspace пустой» держалось только триггером. Добавлено ограничение `Monitor_client_requires_workspace`. Повторный прогон SQL и тестов после этого прошёл.

Открытых дефектов P0, P1 и P2 нет. Вердикт: **PASS**.

Это не доказательство отсутствия любых будущих ошибок. Авторизации workspace в API ещё нет, потому что ни один текущий маршрут эти поля не записывает.

## 2. Phase 1 Implementation Summary

Добавлены таблицы `Workspace` и `Client`. У `Monitor` два nullable-поля. `userId` и `teamId` не менялись. Планировщик, fetch, AI, Stripe и Clerk не менялись.

Целостность:

- клиент без workspace нельзя сохранить;
- клиент другого workspace нельзя сохранить, пока сам клиент существует;
- клиент не переносится в другой workspace;
- удаление workspace сначала обнуляет связи мониторов, затем удаляет только своих клиентов;
- снимки и `Change` остаются.

## 4. Architecture Review

Проверялось чтением схемы, `src/lib/tenancy.ts`, `src/app/api/monitors/[id]/route.ts`, `src/lib/validations.ts`, `src/lib/account.ts` и grep по `workspaceId` в `src`.

`monitorTenancyError` ни один маршрут не вызывает. Это не дыра текущего API: Zod-схема обновления монитора не содержит `workspaceId` и `clientId`, лишние поля отбрасываются. Запись возможна только прямым доступом к базе. Проверка «какой пользователь имеет право поставить связь» относится к Phase 2.

## 5. Prisma Schema Review

Файл: `prisma/schema.prisma`.

- `Workspace.ownerId` обязателен, индекс есть, `ON DELETE CASCADE` к `User`.
- `Client.workspaceId` обязателен, `ON DELETE CASCADE` к `Workspace`. Уникальность `(id, workspaceId)` нужна как пара для возможного составного ключа; первичным ключом остаётся `id`.
- `Monitor.workspaceId` и `Monitor.clientId` nullable, отдельные индексы, `ON DELETE SET NULL`.
- `settings Json?` в Postgres соответствует `JSONB` в SQL.
- `@updatedAt` обновляет Prisma при записи через клиент. Сырой SQL сам по себе `updatedAt` не двигает. На целостность это не влияет.

Схема не описывает триггеры. Они есть только в SQL. Это расхождение Prisma и базы, не потеря ограничения: повторный `db execute` этого файла создаёт триггеры снова.

## 6. Migration SQL Review

Файл: `prisma/migrations/20261113160000_workspace_client/migration.sql`.

Сверено со схемой: таблицы, колонки, индексы, четыре внешних ключа, check, три функции и три триггера.

Новые колонки монитора nullable и без значения по умолчанию. Для Postgres это не переписывает старые строки и не подставляет им workspace.

Повторный запуск того же файла на локальной базе `127.0.0.1:54329` завершился без ошибки. Объекты создаются через `IF NOT EXISTS` и `duplicate_object`.

Конфликта имён с предыдущими миграциями по тексту файлов нет. Полный `prisma migrate deploy` по всей истории локально не запускался: эта база собиралась через `db push`, а ранние миграции инкрементальные. Это ограничение способа проверки, не дефект нового SQL.

Триггеры создаются как `EXECUTE PROCEDURE`, чтобы файл применялся и на версиях Postgres, где `EXECUTE FUNCTION` ещё не принят. Повторное применение на локальном Postgres 18 прошло.

## 7. Production Deployment Compatibility

Проверялось чтением `vercel.json` и `package.json`. Секреты не читались и не печатались.

- `vercel.json` задаёт `buildCommand`: `npm run build`.
- `npm run build` — это `prisma generate && next build`. Миграций нет.
- `vercel-build` содержит `prisma migrate deploy`, но этот скрипт текущий `buildCommand` не вызывает.
- `db push` на прод по правилам не используется и в этом аудите не запускался.

Порядок выкладки: оператор отдельно применяет эту миграцию к продовой базе, убеждается, что таблицы есть, и только потом деплоит код, который их читает. Если код выкатить раньше, старый Prisma-клиент на проде при чтении `User` не знает новых колонок монитора и не обязан падать; новый клиент упадёт, пока таблиц нет. Поэтому код с новой схемой не должен выходить раньше миграции.

Откат деплоя после успешной миграции разобран в разделе 20.

## 8. Backward Compatibility

Доказательства на локальной базе, не на проде.

Старый писатель смоделирован сырым `INSERT` в `Monitor` без `workspaceId` и `clientId`. Тест `an insert that omits tenancy columns succeeds`: строка создалась, оба поля `NULL`.

Триггер висит только на `INSERT OR UPDATE OF clientId, workspaceId`. Обновление `lastCheckedAt`, статуса и очереди его не вызывает. Код планировщика, fetch и AI по grep не упоминает новые поля.

Существующий монитор `https://example.com` прочитан в тесте: `workspaceId` и `clientId` остались `NULL`, `userId` непустой.

Zod по-прежнему не принимает tenancy-поля. Stripe webhook paths, Clerk и Team routes не редактировались в этом аудите.

Не доказано бинарником предыдущего релиза: старый собранный сервер здесь повторно не запускался. Доказана совместимость формы старой записи с новой таблицей.

## 9. Workspace Integrity

Тест создал workspace с `ownerId` тестового пользователя. Без пользователя внешний ключ не даст строку: отдельный негативный insert без владельца в этом прогоне не выполнялся, опора на `Workspace_ownerId_fkey`, который тест видит в `pg_constraint`.

У одного владельца может быть несколько workspace. Уникальности имени нет. Это не ошибка целостности.

Удаление владельца каскадом удаляет его workspace. Мониторы этого пользователя и раньше удалялись каскадом по `userId`. Тест `deleting the test user removes that user's monitor` это подтвердил для тестового пользователя. Чужие мониторы этот каскад не трогает, потому что у них другой `userId`.

Участников workspace нет. Это Phase 2, не дыра текущей записи.

## 10. Client Integrity

Тест: client создаётся только с `workspaceId` существующего workspace. Обязательность поля и внешний ключ `Client_workspaceId_fkey` подтверждены выборкой из `pg_constraint`.

Смена `workspaceId` у клиента запрещена триггером `client_workspace_immutable`. Отдельный тест на UPDATE клиента не добавлялся; триггер есть в `pg_trigger`. Это более слабое доказательство, чем попытка UPDATE. Риск низкий, потому что API клиента нет. Классификация: P4, не блокер.

Удаление клиента обнуляет `Monitor.clientId` и не удаляет монитор. Тест это прошёл. Удаление workspace удаляет клиентов. Тест `clients of a deleted workspace are removed` прошёл.

## 11. Monitor Relationship Integrity

Проверенные комбинации на локальной базе:

| workspaceId | clientId | Результат теста |
| --- | --- | --- |
| NULL | NULL | разрешено, старый и новый монитор |
| задан | NULL | разрешено после удаления клиента |
| задан | клиент этого workspace | разрешено |
| задан | клиент другого workspace | отклонено, строка не изменилась |
| NULL | задан | отклонено |
| смена workspace при оставшемся clientId | — | отклонено |

Составной внешний ключ не используется: при `ON DELETE SET NULL` он обнулил бы оба столбца сразу и при удалении клиента стёр бы workspace. Поэтому соответствие клиента и workspace держит триггер, а запрет пустого workspace при заполненном client — check.

## 12. DB Trigger Review

`monitor_tenant_guard` срабатывает на INSERT и на UPDATE `clientId` или `workspaceId`.

Если `clientId` пустой, триггер ничего не запрещает. Так монитор может лежать в workspace без клиента и может быть полностью отвязан.

Если клиент существует и его workspace не равен `NEW.workspaceId`, операция отклоняется. `NULL` считается отличным значением, поэтому клиент без workspace тоже отклоняется. Это продублировано check-ограничением.

Если строки клиента уже нет, триггер пропускает строку дальше, и внешний ключ `Monitor_clientId_fkey` не даёт сохранить висячий id.

Обход триггера приложением не найден: маршруты поле не пишут. Владелец таблицы может отключить триггер в SQL. Check при этом всё ещё запрещает пару «client без workspace», но не пару «чужой client + его workspace». Для этой пары триггер обязателен. Отключение триггера суперпользователем не считается дырой приложения.

Гонка «клиент удалён между проверкой и записью» закрывается внешним ключом, не триггером. Гонка «клиент переехал в другой workspace» закрыта запретом менять `Client.workspaceId`.

Prisma эти триггеры не генерирует. Они приезжают только с SQL-файлом.

## 13. Delete Behavior Review

На локальной базе, один тестовый пользователь, затем удаление этого пользователя:

1. Удаление client: монитор остался, `clientId` стал NULL, `workspaceId` сохранился.
2. Удаление workspace: монитор остался, оба поля NULL.
3. У этого монитора после удаления workspace остались 1 snapshot и 1 change.
4. Повторное удаление того же workspace отклонено, монитор на месте.
5. Удаление пользователя удалило его тестовый монитор. Это прежний каскад `Monitor.userId`, не каскад workspace.
6. Снимки чужого продакшен-монитора не изменялись. Локальный `https://example.com` только читался.

Уведомления на удалённом тестовом мониторе отдельно не создавались. Их внешний ключ по-прежнему идёт к `Change` и `User`, не к workspace. Потеря уведомлений при удалении workspace из схемы не следует. Отдельной строки notification в тесте не было. Это указано как неполная проверка, не как дефект.

## 20. Migration Recovery Strategy

Сценарий: миграция на проде применена, новый деплой Vercel упал, сайт остался на прошлом билде.

Старый код не выбирает и не записывает новые колонки. Новые колонки nullable. Триггер не срабатывает на обычное обновление монитора. Пустые таблицы workspace ничего не меняют в проверках. Сайт остаётся работоспособным.

Откатывать миграцию не нужно. Удаление таблиц после того, как в них появились строки, сотрёт клиентов и может задеть связи. Если деплой нового кода упал, исправляется сборка, а схема остаётся.

Если миграция применилась наполовину, повторный запуск того же SQL безопасен: он идемпотентный. Это проверено локально, не на проде.

Не делать `db push` на прод.

## 23. Remaining Risks

- Прод ещё без этой миграции. Выкладка нового Prisma-клиента до миграции сломает запросы, которые начнут читать новые таблицы. Старый билд после миграции, наоборот, должен жить.
- Версия Postgres на проде этим аудитом не снималась. Файл использует `EXECUTE PROCEDURE`. Если прод окажется старше синтаксиса триггеров в файле, миграция остановится до записи новых объектов или на создании триггера. Тогда новый код не выкатывают, пока SQL не пройдёт. Откат данных не требуется, если транзакция миграции откатилась целиком. Prisma по умолчанию выполняет миграцию в транзакции. Это свойство Prisma, локально отдельным обрывом транзакции не проверялось.
- Прямой доступ к базе может связать монитор с чужим, но согласованным client и workspace. HTTP этого не делает.
- История `_prisma_migrations` на локальной базе этим аудитом не читалась. Не доказано, что Prisma уже считает файл применённым. Повторный SQL при этом безопасен.
